## Part 1 — Epic 1 Review

### What Went Well

1. **Planning en amont + ATDD = base solide**
   Épics et stories bien définis (AC en Given/When/Then, Dev Notes avec patterns exacts) ont permis au dev agent d'implémenter sans allers-retours. Les tests ATDD écrits en amont ont rendu les code reviews rapides et fiables. Même quand les APIs TanStack Start différaient de ce qu'on attendait, les critères d'acceptation restaient stables.

2. **Progression de qualité marquée au fil de l'épic**
   Story 1.1–1.3 : issues Critical et High trouvées en review, plusieurs rounds nécessaires. Story 1.4 : **APPROVED au premier round, 0 Critical, 0 High**. Le dev agent a intégré les leçons des stories précédentes.

3. **Patterns architecturaux émergents et cohérents**
   `middleware.ts` (middlewares centralisés), `queries.ts` (accès DB nommés), `types.ts` (`ServerResult<T>`) — ces patterns n'étaient pas planifiés au départ. Ils ont émergé des code reviews de story 1.3 et constituent maintenant une fondation cohérente pour l'Épic 2.

4. **Zéro régression cross-stories**
   126 tests au total, aucune régression d'une story à l'autre. Le baseline de tests croissant a protégé les stories suivantes.

5. **Infrastructure de qualité livrée**
   CI/CD (GitHub Actions + Railway), design system (palette tokens + fonts), auth complète, admin opérationnel — tout ce qui était dans le scope de l'Épic 1 a été livré à 100%.

### Challenges

1. **API TanStack Start (RC) — friction constante**
   Chaque nouvelle feature a nécessité un `search-docs` pour vérifier l'API réelle. Exemples : `.inputValidator()` au lieu de `.validator()`, cookies depuis `@tanstack/react-start/server` et non `vinxi/http`, `createMiddleware({ type: 'function' })`. Ce n'est pas des bugs mais du friction de découverte constant sur un framework en RC.

2. **Import-protection pattern découvert trop tard**
   Le pattern a été découvert en story 1.2 quand le build a cassé. Si ce pattern avait été documenté dès story 1.1, les stories 1.2 et 1.3 auraient eu moins de friction. C'est un gotcha invisible à l'implémentation.

3. **Règles d'architecture documentées mais pas toujours respectées**
   Malgré la documentation explicite ("src/db/ is the ONLY directory that imports drizzle-orm"), story 1.2 a quand même importé `db` directement dans `login.tsx`. La documentation seule ne suffit pas — il faut des garde-fous exécutoires.

4. **`armyOwnerMiddleware` en pass-through**
   Scaffoldé depuis story 1.2, le middleware est branché mais laisse tout passer. C'est de la fausse sécurité : le code existe mais ne protège rien. À compléter impérativement en story 2.1.

### Key Insights

- **Documentation seule ≠ compliance.** Les règles d'architecture ont besoin de tests d'architecture (import-checks dans les tests d'intégration) ET de Dev Notes explicites ("NE PAS importer X dans ce fichier") pour être efficacement respectées.
- **Les patterns émergent des reviews.** Les meilleures pratiques (middleware.ts, queries.ts) n'ont pas été planifiées — elles ont émergé. Le processus de review est un levier d'amélioration architecturale.
- **La qualité s'améliore au fil des stories quand les leçons sont documentées.** Story 1.4 est la preuve qu'un dev agent peut intégrer les apprentissages des stories précédentes si ces apprentissages sont capturés dans les story files.
